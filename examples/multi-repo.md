# Fictional example: Canvas and Geometry

A new curve primitive spans a library and its desktop consumer. The parent outcome is rendering and editing that primitive. The library owns its API/tests; the application owns interaction. A tracker coordinates order without establishing either implementation's completion.

Use a compact plan, current status and focused API record. Name the library change, consumer change and integration checkpoint. Keep exact versions in the compatibility owner and commands in each repository's development guide.

The library kickoff may be executable now. The consumer kickoff stays provisional until the API and prerequisite candidate settle. Do not generate every future kickoff against current soon-stale source.

Library tests do not establish application interaction. Record the actual consumed revision. A later API change invalidates affected consumer evidence even without another consumer commit.

If manual editing verification is unavailable, state implementation complete with interaction unverified, name the required observation and withhold a user-visible completion claim.

A workspace registry, dependency controller and bounded progress view could help here. Build them as separate tested slices; a coordinator does not need every worker transcript to identify the next admissible action.
