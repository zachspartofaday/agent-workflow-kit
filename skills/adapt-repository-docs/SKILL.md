# Adapt repository documentation

Establish the target repository and the user's intended outcome. Inspect existing agent instructions, contribution/development docs, build configuration, current work, decisions and the working-tree diff before proposing a layout.

## Map before editing

Map these roles to existing owners: durable rules/routing; exact commands; current work/blockers/next action; design rationale; historical evidence; review/closeout. Filenames are flexible. Reuse existing owners rather than create parallel guidance. A small task may use its active issue as current status.

For each role report existing path, observed evidence, proposed action, preserved requirements and unresolved conflicts. Identify the current authority behind conflicting text. Ask only when inspection cannot settle a material choice. The kit's preferences never override stronger local requirements.

## Apply the accepted mapping

Use existing authorization; obtain a decision when scope or consequential action requires it. Read current file contents and diff before edits. Preserve unrelated changes, historical decisions and command implementations. Do not migrate repository structure merely to fit this skill.

Create only missing document roles. Do not invent commands, policy owners, package versions or completed validation. Missing facts stay named gaps with a clearing action. Reference the real command owner instead of duplicating commands elsewhere.

Check links, command references and preserved requirements. Verify the actual affected checks where available. On repeated adoption, reconcile existing owners and avoid duplicate files or completion chronology in current status.

## Output

Provide before/after ownership, changed paths, preserved constraints, validation actually performed, gaps and next action. Distinguish an accepted mapping from an applied migration. Do not install extensions or modify global agent settings as a side effect.
